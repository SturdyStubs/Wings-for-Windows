# Disposable VM reboot validation

The operator authorized reboot testing after alpha 27. Earlier deferrals remain historical evidence; they are not the current instruction. Reboot gates stay open until exact results are recorded.

The developer fixture offers opt-in `-PrepareReboot` with persistent recovery, console logging and service events enabled. Use a fresh disposable fixture only. Run the normal combined service fixture separately first. This mode retains its own service/accounts/credentials for a two-phase test; it does not reboot by itself. The operator must explicitly reboot the intended VM after inspecting its prepared report.

The fixture adds a unique console marker, keeps the consumed two-attempt recovery budget and leaves the game offline. It configures its dedicated daemon service for delayed automatic start, registers an at-startup SYSTEM loopback mock task, and a hidden SYSTEM resume task delayed three minutes. The resume task checks that the host boot time changed, the daemon automatically started under its non-administrator SID, games/timers remain offline, history and budget were restored, and a manual launch uses the stored credential under a separate game account after a cold profile load. It checks root/child identity and stop behavior, then attempts cleanup without requiring SSH or interactive login.

To permit unattended credential removal, the disposable daemon password is transiently protected using machine-scoped DPAPI in `private/reboot/state.json`. Its new directory grants access only to SYSTEM and Administrators; it is not readable by the game or daemon account. Machine DPAPI alone is not an account boundary: the DACL is essential. No plaintext password, token, filled node config or encrypted credential state belongs in source control or public evidence. The state file is deleted after verified credential/service cleanup. Do not copy it to another host.

Preparation refuses existing fixture roots/accounts/tasks/services and checks exact service identity/path. The resume script checks pinned account SIDs and daemon hash/path before operating. It removes the exact game credential through the public helper, deletes its service, removes its two reboot tasks and exact mock process, removes its Event Log source/accounts/rights, and deletes encrypted cleanup state. No profile is force-unloaded/deleted and historical events remain. If a cleanup stage fails, retain state for inspection and report the failing gate rather than declaring success.

Inspect `scm-report.json` for `reboot_prepared`, and `reboot-report.json` after the delayed task. A prepared report is not a completed reboot result. The task has a 15-minute execution limit; a failed task or unavailable SSH requires inspection, not an assumption of cleanup. Confirm SSH reconnect and an independent cleanup audit after boot.

This tests the documented delayed-start deployment with a loopback mock and harmless demo. The default mode leaves games offline; alpha 29 adds opt-in running restoration as described below. It does not certify immediate-start dependency races, real panel/TLS/game behavior, host power-loss recovery, account-password rotation or full reboot/isolation parity. Installation still defaults to Manual start; the fixture changes only its own temporary service. Actual results are recorded in [verification](VERIFICATION.md).

Alpha 28 actual results: the VM boot time changed, pinned SSH reconnected, all seven post-boot checks and both cleanup verifications passed. See [exact package/source results and remaining gates](evidence/server2022-alpha28-xml-reboot.md). This supersedes the former deferral for the tested scenario; broader recovery gates remain open.

Alpha 29 adds an opt-in `-TestRestoreRunning` fixture mode. It leaves a running intent/game before reboot and expects a fresh automatic game launch under the separate SID, a new persistent reservation and a confirmed stopped intent after post-boot stop. The default/offline fixture remains supported. See [restoration](RUNNING-RESTORATION.md).

Alpha 29 actual results: all 44 preparatory and seven post-boot checks passed, including automatic running-game restoration under the separate identity and a new persistent reservation. Pinned SSH reconnected and unattended/independent cleanup passed. See [exact results and limits](evidence/server2022-alpha29-running-restoration.md).
