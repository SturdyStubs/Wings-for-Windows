# Optional Windows pseudoconsole

Alpha 56 adds `"pseudoconsole": true` to an operator-approved native game profile. Omitted/false preserves existing pipe stdio. It is useful for console applications that call Windows Console APIs rather than reading anonymous stdin pipes. It does not turn arbitrary Windows GUI applications into console servers.

Requires the Windows ConPTY APIs (Windows 10 version 1809 / Server 2019 or newer); supported-host certification still follows the project matrix. The fixed terminal is 120 columns by 40 rows. No interactive desktop window is requested. Process creation remains suspended until assigned to the existing Job Object, using the same optional restricted game identity, launch guards, CPU/memory limits and network policy. The process attributes carry only the pseudoconsole; arbitrary inheritable handles are not passed to the child.

When the parent runs with redirected stdin/output, explicitly supply invalid/empty standard-handle placeholders with STARTF_USESTDHANDLES so ConPTY can provide the attached console instead of copying the parent's redirected handles. The redirected-parent edge case is discussed in [Microsoft Terminal](https://github.com/microsoft/terminal/discussions/15814). The Windows API preparation is based on [Microsoft's pseudoconsole session documentation](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session). Commands use a carriage return as Enter; pipe mode retains CRLF.

A background worker always drains the terminal into a buffer bounded to 256 KiB of raw output plus a truncation marker. A slow or closed log consumer loses old output rather than blocking ConPTY. Output remains UTF-8/VT terminal data; existing readiness matching removes supported ANSI sequences, but this is not a full terminal-screen reconstruction engine. Cursor redraws, wrapped lines and application-specific console behavior can still need adapters. Conhost overhead is outside the game's root-process metrics; aggregate accounting remains open.

On process exit the existing job cleanup kills remaining descendants, then closes the pseudoconsole on its wait goroutine while output continues draining. This addresses the older-host deadlock documented for [ClosePseudoConsole](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole). Native calls are not forcibly interruptible, so no hard shutdown latency guarantee is claimed. InstallerProfile intentionally constructs pipe-only recipes; enabling the game adapter does not change installation semantics.

## Game compatibility findings

Official OpenTTD 15.3 Windows amd64 plus OpenGFX 8.0 were obtained from the project's HTTPS distribution with published SHA256 verification. A local direct native-process diagnostic starts the actual executable and observes a loopback game listener, but its official Windows GUI build does not forward console output/commands correctly through the tested transports. Inspect its platform CreateConsole/CRT initialization and consider a supported console build or a game-specific control adapter before approving a runnable panel profile. Do not infer successful graceful stop, save/reload, panel installation or playability from a listening port.

The console adapter has a dedicated native Windows fixture that uses GetConsoleMode/ReadConsoleW/WriteConsoleW, separate from the ordinary stdio demo. A real-game lifecycle remains an open milestone. Keep the private/trusted-node restriction. The optional [diagnostic tool](../tools/native-realgame-probe/README.md) is not a package downloader, installer or general-purpose game launcher.
